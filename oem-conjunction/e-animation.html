Approach E · walkthrough

How a count of orbital close approaches gets computed without anyone but one key holder ever seeing a position

This traces one real run of 13_multi_approach_e_openfhe_bootstrap.py on two live Starlink satellites, step by step, with the actual numbers it produced — not a stand‑in diagram. Every number on this page comes from the report or the script's own output.

01

The question two operators actually have

STARLINK‑35712 and STARLINK‑3845 pass near each other seven times over a six‑hour window. Each operator has their own position table (an OEM) for their own satellite. Neither wants to hand the other their raw ephemeris — that leaks the satellite's future track. What they both want is a single yes/no per encounter: does the miss distance ever drop under 10 km?

A plaintext SGP4 search on the real TLEs finds the seven local minima below. Each gets a ±40 s window sampled every 10 s (9 points), so the whole problem is 63 candidate times, packed together into one encrypted computation.

Two of these are the interesting ones for the rest of this page: cluster 3, the real 5.432 km violation, and cluster 6, the closest genuine safe — only 1.698 km outside the fence. Everything downstream has to get both of these right without ever decrypting a position to check.

02

What this looks like with no encryption at all

Strip away CKKS entirely and the algorithm is ordinary orbital mechanics, four steps, done once per candidate time:

1. Sample positions near the query time. Each operator already has position samples around each candidate time t from their OEM.
2. Interpolate to exactly t. The query time usually falls between samples, so both operators fit a Lagrange polynomial through their nearby samples and evaluate it at t, giving (x₀,y₀,z₀) and (x₁,y₁,z₁).
3. Compute squared distance. d² = (x₀−x₁)² + (y₀−y₁)² + (z₀−z₁)². For cluster 3, the real interpolated positions give d² ≈ 29.51 km² — a miss distance of 5.432 km.
4. Compare to the threshold. d² < 10² = 100? For cluster 3, 29.51 < 100 — violation. For cluster 6, 11.698² ≈ 136.84, so 136.84 < 100 is false — safe, but only by 36.84 km² of margin.

On plaintext numbers, step 4 is trivial: it's an if statement. The entire rest of this page exists because CKKS ciphertexts cannot run that if.

03

Why you can't just do that on ciphertext

CKKS gives a host exactly two operations on encrypted data: add and multiply. That's it. There is no encrypted <, no encrypted if, no encrypted sign(). Comparison and branching both require inspecting a bit of the underlying number — the sign bit, or a bit of the difference — and CKKS ciphertexts don't expose bits. They only expose arithmetic.

So step 3 (distance²) survives unencrypted arithmetic untouched: subtract, square, add — all multiplications and additions. Step 4 (the comparison) is the wall. The fix used here is to replace "is this number negative" with "compute a function that behaves like the sign of this number, using only adds and multiplies."

04

Faking a comparison with a polynomial

Before comparing, the script rescales d² − threshold² down to a small number: x = (d² − 100) / 5,000,000. That division isn't cosmetic — the sign polynomial below is only accurate for inputs near zero, so every distance in the batch gets compressed into that range before any comparison is attempted.

cluster 3 · violation
d² = 29.51  →  (29.51 − 100)/5,000,000 = −1.41×10⁻⁵
cluster 6 · near‑miss safe
d² = 136.84  →  (136.84 − 100)/5,000,000 = +7.37×10⁻⁶

That's what "the encrypted value" actually is at this point in the pipeline: not a distance, not a flag — a tiny signed number, encrypted, whose sign is the only thing that matters and whose magnitude is still statistically indistinguishable from zero. A single tiny negative number is not a trustworthy encrypted "true." The rest of this chapter is about turning that sign into a confident ±1 without ever decrypting it to look.

The tool for that is g(x) = (3x − x³)/2, a cubic that behaves like a soft sign function: near zero its slope is 1.5, so it amplifies small values outward, and it's flat near ±1, so once a value gets close to ±1 it stays there. Composing it with itself — feeding its own output back in — repeatedly pushes any nonzero number toward its sign, sharpening a little more each round.

On this exact pair, after the first composition the report's own decrypt-and-check run recorded:

Composition 1: the 5.432 km violation reads −4.8×10⁻⁵. The 11.698 km safe reads +2.5×10⁻⁵. Both signs are already correct — but a number that small cannot be summed across 63 slots and read as a count. One stray bit of CKKS noise could flip it.

So the script composes g eleven times in a row (TOTAL_COMPOSITIONS = 11), and different events need different amounts of sharpening:

That's the actual reason the pipeline runs eleven rounds instead of one: the hardest cases here are barely on either side of the line.

05

What a CKKS ciphertext is, concretely

A CKKS ciphertext here is not one encrypted number. It's an encrypted vector of up to 4,096 real numbers (the slot count for this run's ring dimension of 213), packed so that adding or multiplying two ciphertexts adds or multiplies every slot in parallel — one instruction, thousands of lanes. That packing is why 63 candidate times can be processed as one ciphertext instead of 63.

Two things ride along with every value:

  • Scale. Real numbers get encoded by multiplying by a large fixed factor and rounding to an integer before encryption, so the arithmetic underneath is exact integer math on a value that decodes back to an approximate real number. That approximation is where the 10−7‑ish noise on every "should be exactly ±1.0" slot comes from — it's visible in the raw per-point flags, e.g. 0.9999999802 instead of exactly 1.0.
  • Level. Every ciphertext also carries a countdown of how many more multiplications it can survive before the encoded noise grows large enough to corrupt the answer. This run starts with roughly 15 levels of budget after setup. Every EvalMult — including every call inside g(x) = (3x−x³)/2, which needs two multiplications per composition — spends one level.

Eleven compositions at two multiplications each is around 22 levels of demand against a ~15-level starting budget. That gap is exactly why bootstrapping exists.

06

Why bootstrapping, and what it actually does

Once a ciphertext's remaining level budget drops below 8 (the threshold this script checks before every composition), it cannot safely absorb another multiplication — the noise would overwhelm the signal and decryption would return garbage. There are only two ways out: stop computing, or refill the budget.

EvalBootstrap refills it. Mechanically, it takes the ciphertext, homomorphically re-runs the CKKS decryption formula itself — as an encrypted computation, using the evaluation keys, never the secret key — and produces a new ciphertext that decrypts to (approximately) the same value but with a fresh, high level budget. It is decryption performed without ever exposing the plaintext: the host runs it, the host never sees the number. The cost is real: it's the single most expensive operation in the whole pipeline and it degrades precision a little each time, which is part of why the 11 compositions need margin, not just enough to reach ±1.

This run bootstraps 3 times across the 11 compositions — exactly when the remaining budget would otherwise fall under 8. Without bootstrapping, this script could not run more than about 6–7 compositions on 63 packed candidate times at these parameters, which per chapter 4 is not enough to safely classify the near-boundary cases.
07

From 63 flags to one encrypted number

After 11 compositions every one of the 63 candidate times sits in its own SIMD slot as (approximately) +1.0 for safe or −1.0 for violation — still fully encrypted, still packed in one ciphertext. Two things happen before this can be decrypted as a single count:

Mask. Each candidate time actually occupies a small block of slots (interpolation intermediates live in the other slots of the block); a plaintext one-hot mask multiplies in 1.0 at slot 0 of each block and 0.0 elsewhere, zeroing out everything that isn't a final flag. This is a plaintext×ciphertext multiply — the mask itself is public, only the flags are encrypted.
Sum. EvalSum adds every slot together, still under encryption. 62 safes contribute +1 each and 1 violation contributes −1: 62 − 1 = 61.

The result of this whole computation, before anyone decrypts anything, is one ciphertext holding one number: 61, out of 63 candidate times. Nobody — not the host running the arithmetic — has learned a single position, distance, or even which of the 63 times was the violation.

08

Decrypting the answer

The key holder decrypts that one ciphertext and gets 60.99999973799246 — not exactly 61, because of the scale noise described in chapter 5, but close enough to round with confidence. From there the count of violations is arithmetic, not decryption: for n candidate times where k are violations, the sum is (n−k) − k = n − 2k. Solving for k:

k = (n − sum) / 2 = (63 − 61) / 2 = 1

One violation, out of 63 candidate times, across 7 real close approaches — matching the plaintext ground truth from chapter 1 exactly, and matching it without the key holder ever learning which of the 63 times it was, or by how much.

09

Who actually holds the key

This is the part worth being blunt about, because the report draws a role diagram — operator, operator, host, key holder — and it is easy to read that as four parties each with their own key. That is not what the code does.

What actually runs: the script calls cc.KeyGen() exactly once. There is one keypair for the entire computation. Both satellites' position data get encrypted under the same public key. There is no "Alice's key" and "Bob's key" — there is one key holder's key, and both operators encrypt with the public half of it.

Where does that key come from? cc.KeyGen() generates it from the crypto context's public parameters — ring dimension, scaling modulus, security setting — set up once at the start of the script. It isn't derived from either satellite's data; it's generated fresh, independent of the two OEM datasets it will later be used to encrypt.

So where do "Alice" and "Bob" get their own encryption keys? They don't, in this build. Both operators are handed the same public key by whoever plays key holder, and encrypt with it. That's a deliberate property of single-key CKKS, not an oversight in the labeling: everyone who encrypts uses the same public key, and exactly one party holds the matching secret key. The two operators are distinguished only by which ciphertexts are theirs, not by which key encrypted them.

Can this be replaced with a scheme where each operator holds their own key? Yes, in principle — that's what threshold FHE or multi-key FHE are for: schemes where decryption requires cooperation from multiple keyholders (or the ciphertext is encrypted under a joint key that no single party controls), so no single key holder can unilaterally decrypt. Generic MPC is another route to the same guarantee without FHE at all. The report says this plainly in its own attack-vectors table: for the "host and one operator collude to decrypt the other operator's data" scenario, the stated status is "would need threshold / multi-key FHE or MPC. Neither is built here." The single-key-holder trust assumption is a real, disclosed limitation of this specific build, not something this page is the first to notice.
