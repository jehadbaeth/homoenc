Can CKKS carry real orbit-propagation traffic — and does it actually keep anything private?

A from-scratch, two-language (Python + Java) implementation of an SGP4-shaped orbit-propagation workload under fully homomorphic encryption, benchmarked for latency, memory, and bandwidth, and checked honestly against what it actually promises to keep confidential.

Abstract

What this study found, in short

Fully homomorphic encryption (FHE) is the one class of technique that lets a server compute on data it never gets to see in the clear. That's an attractive property for any service that processes sensitive numerical data on someone else's behalf — orbital tracking data is one example, medical sensor data or financial positions would be others. This study picks a concrete, non-trivial workload — an SGP4-shaped orbit-propagation computation, chosen because it involves an iterative solve that FHE cannot do directly — and asks two separate questions about it: what does it cost, and what does it actually keep confidential? We built the same staged prototype twice, once in Python against TenSEAL and once in Java against Microsoft SEAL directly, and benchmarked both under an identical CKKS context on the same machine. On cost: correctness holds up to sub-meter accuracy and the workload's statelessness makes scaling arithmetic trivial, but compute is roughly five orders of magnitude above the plaintext equivalent, and multiplicative depth is a fixed, pre-committed budget rather than a knob you can turn at runtime. On confidentiality, the honest answer is more mixed than the pitch: the technique used here to work around FHE's lack of division requires the object's orbit shape to be known in the clear, and only its phase — where it is along that orbit right now — stays encrypted. Whether that's an acceptable tradeoff depends entirely on the threat model, and in the cases where confidentiality would matter most, it probably isn't one. Section-by-section detail, all measured numbers, and an honest bad/good findings list follow below.

Background

The problem this addresses

Ordinary encryption (AES, TLS, disk encryption) protects data at rest and in transit, but a server that needs to compute on that data has to decrypt it first. Anyone who wants a third party to run a computation without seeing the input — a cloud provider, an analytics vendor, a shared processing service — normally has to either trust that party with the plaintext or keep the computation in-house. Fully homomorphic encryption removes that requirement: it lets specific arithmetic operations (addition, multiplication) run directly on ciphertexts, producing an encrypted result that decrypts to the same answer as if the operation had run on the plaintext.

CKKS is the FHE scheme used throughout this study. It's built for approximate arithmetic over real numbers rather than exact integers, which makes it a natural fit for physical/engineering computations that already tolerate floating-point error. Its two hard constraints shape everything else in this report:

1. Multiplicative depth is finite and fixed in advance. Every ciphertext-ciphertext multiplication consumes one "level" from a budget baked into the encryption context at setup time — this context supports exactly 16 sequential multiplications, no more, ever, without re-encrypting under a bigger (and much more expensive) context.

2. There is no ciphertext/ciphertext division, and no comparison or branching. Anything that needs "divide by an encrypted value" or "if this encrypted value is greater than that one" cannot be expressed directly. That single restriction is why this study exists: real orbit propagation needs exactly that kind of operation, and working around it is the actual engineering content of this project, not a footnote.

We picked orbit propagation as the test workload specifically because it is not a toy "add two encrypted numbers" demo. SGP4-style propagation includes solving Kepler's equation (M = E − e·sin(E)) for the eccentric anomaly E, which is normally done with Newton–Raphson iteration — a loop that repeatedly divides by an encrypted quantity and decides when to stop based on comparing an encrypted error to a threshold. Neither operation exists under CKKS. Forcing a real iterative numerical method through FHE's constraints, rather than picking a workload that avoids the problem, is what makes the findings below meaningful.

What was built

A staged prototype, twice

Rather than trying to encrypt the full Newton–Raphson loop directly (which doesn't work — see above), the prototype takes a different route, arrived at through a sequence of staged experiments that each hit a specific wall and then worked around it:

Stage 0 — round-trip sanity. Encrypt a number, decrypt it, confirm CKKS's approximate arithmetic introduces only the expected small numerical noise. Establishes the error budget everything else is measured against.

Stage 1–2 — linear operations. Confirm addition, subtraction, and plaintext-multiplication work homomorphically as expected on orbital quantities, and measure how much precision each operation costs.

Hitting the wall. Attempting Newton–Raphson for Kepler's equation directly under encryption fails immediately: it needs division by an encrypted value at every iteration, and needs to decide when to stop, which CKKS cannot express. Decrypting an intermediate value to check convergence defeats the entire point of encrypting the input.

Stage 3 — the actual fix: closed-form polynomial evaluation. Instead of solving Kepler's equation homomorphically, fit its solution as a polynomial offline, in plaintext, for a known, fixed orbit shape (semi-major axis a, eccentricity e) — sampling the true solution at many values of mean anomaly M and fitting a degree-14 polynomial in M with ordinary least squares. At runtime, only M is encrypted; the server evaluates the pre-fit polynomial homomorphically using nothing but ciphertext add, multiply, and plaintext-multiply — all operations CKKS actually supports — via Horner's method. This is the core trick this whole study is built around, and it's also the source of the confidentiality limitation discussed below.

Stage 4+ — extending to a second hidden variable. The same idea, extended to also keep eccentricity e encrypted (not just M), fitting a two-variable (bivariate) polynomial and evaluating it homomorphically over a small pre-agreed range of e. This works, but costs more multiplicative depth per evaluation, and widening the eccentricity range further (attempted, and it's what stage 6 in the source tries) needs more depth than this context's 16-level budget can supply — it fails deterministically, in both languages, exactly as depth theory predicts.

The whole thing was built twice, independently: once in Python against TenSEAL (a high-level Python wrapper over Microsoft SEAL), and once in Java, hand-written against SEAL's C ABI (sealc) via a JNA binding, because no mature native Java FHE library exists. Building it twice wasn't redundant busywork — it's what let us tell, later, whether a given finding was a property of CKKS itself or an artifact of one particular binding (see the Latency section: some findings turned out to be algorithmic, not language-related, and building both was the only way to know that).

Privacy model

What actually stays confidential — and what doesn't

This is worth stating plainly and early, because it's easy to read "encrypted orbit propagation" and assume it means the orbital data is confidential end to end. It doesn't. Stage 3's fix — the one everything past it depends on — requires the orbit's shape parameters (a, e) to be known in the clear, in order to build the offline polynomial fit. Only the orbital phase (mean anomaly M, and in the extended stage, e within a narrow pre-agreed band) is ever encrypted. The server that evaluates the polynomial always knows what kind of orbit it's evaluating; it only doesn't know exactly where along that orbit the object currently is.

Does that matter in practice? It depends entirely on what's actually sensitive, and the honest answer splits into two very different cases:

For an object that's already in a public catalog (tracked and published via Space-Track or CelesTrak TLEs, which cover essentially everything trackable from the ground), semi-major axis and eccentricity are already public information. Handing them to the evaluating server in the clear doesn't leak anything about that object's orbit that a public catalog lookup wouldn't already reveal. In this case the design's actual, real confidentiality contribution is protecting the object's current position from the server — which can be a genuinely useful property (e.g. not wanting a shared computation provider to know exactly where something is right now), just a narrower one than "the orbital data stays private."

For anything else, this breaks down — and these are exactly the cases where someone would actually want confidentiality in the first place:

  • Undisclosed or uncataloged objects. A newly launched, not-yet-cataloged, or deliberately undisclosed object's shape parameters are themselves the sensitive fact. This design requires exposing exactly that fact to build the fit.

  • Query-to-object linkage. Even for a cataloged object, revealing (a, e) on a per-request basis tells the evaluating server which specific object a given customer is asking about. That link between "this customer" and "this object" may be sensitive on its own, independent of whether the orbital elements themselves are public anywhere else.

  • Precision beyond the public record. The polynomial fit needs shape parameters precise enough to keep the fit's error within budget, which can exceed the precision of public TLEs. In that case the server sees a more refined orbital solution than is publicly available — itself a potentially valuable, proprietary piece of information (e.g., revealing precise station-keeping behavior), not something that was already public.

How big is the "undisclosed object" case, actually?

It would be easy to wave the first bullet above away as an edge case — a handful of spy satellites, irrelevant to most real traffic. The numbers say the opposite: uncataloged objects are the overwhelming majority of everything in orbit, not a rare exception.

Of everything actually in orbit, only around 40,000–50,000 objects are in the public catalog (tracked by the US Space Surveillance Network and published via Space-Track / CelesTrak). Statistical models from ESA and NASA estimate roughly 1.2 million untracked fragments between 1–10 cm, and over 140 million fragments smaller than 1 cm — none of them cataloged, individually identifiable, or trackable by anyone. Cataloged objects are well under 1% of everything up there by count.

On top of that debris population sits a separate, much smaller category: objects that function normally and are cataloged as existing, but whose mission (and sometimes precise orbital elements) is deliberately classified. TLEs carry a classification flag — U for unclassified, S for secret — and S-flagged objects don't appear in the public feed at all. As one concrete, countable example: the NRO alone had roughly 486 cataloged objects in orbit as of mid-2026, about 307 of them active — and that's just the cataloged fraction of one nation's reconnaissance fleet; several other nations run comparable programs, and independent trackers periodically surface individual objects that were never officially acknowledged (the ~170 Starshield satellites identified via radio signal in 2025 being one recent example).

So "the object is undisclosed" isn't a corner case that only applies to intelligence agencies — it's the default state of almost everything in orbit, once you count debris. Combined with the query-to-object linkage and precision points above, the privacy limitation described here applies to most of the space environment, not a small slice of it.

The conclusion we draw from this, stated as plainly as we can: this technique protects orbital phase, not orbit identity, and it should not be described or sold as "orbital data stays encrypted end to end" without that caveat attached. It's a legitimate, useful privacy property in the narrow case where shape is already public and only real-time position needs hiding — and it is not a solution at all in the case where the shape itself, or the fact of tracking a particular object, is what needed protecting. We haven't tested mitigations (encrypting shape too runs into the depth wall at low degree, as stage 4+ shows; coarser public bucketing by orbital regime instead of exact elements is untried), so we're not claiming a fix exists — only naming the limitation honestly instead of leaving it implicit.

Experimental design

What was actually measured

Both stacks run the identical CKKS context: poly_modulus_degree = 32768, coefficient modulus [60, 40×16, 60] bits (18 primes, 16 usable sequential multiplications), initial scale 2⁴⁰. Same host, same run session, back to back, so the numbers are directly comparable to each other — they are not a claim about FHE performance in general.

A real bug this benchmark found: the first version of the Java benchmark OOM‑killed itself (exit 137) a third of the way through. SEAL's C API has no garbage collection across the JNA boundary — every ciphertext returned by a native call is a heap allocation the caller must free explicitly. The staged prototype code never freed anything, which didn't matter for a program that ran once and exited, but a benchmark that repeats multiply() and a 14‑degree Horner evaluation 35 times leaked full‑level ciphertexts (~9 MB each) by the hundred. Fixed by adding explicit Ciphertext_Destroy calls at every intermediate step in multiply(), the Horner evaluator, and the bivariate evaluator — verified against unchanged numerical output before trusting any timing from it.

The crossover is the interesting part: Java is 2.1× faster on the single‑variable evaluation but 1.9× slower on the bivariate one. That's not a language or JIT effect — both run the same native SEAL calls, and the primitive multiply benchmark above shows Java and Python within 5% of each other. It's an algorithm difference: the Java bivariate evaluator pads every term to an identical rescale count with extra dummy multiplications against a freshly encrypted 1.0 (needed to keep every term's scale field bit‑identical before summing — see the Java prototype notes), while the Python version's power_ladder approach does fewer total ciphertext multiplies for the same result. The lesson generalizes: at this workload's scale, how you structure the multiplication tree matters far more than which language calls libSEAL.

Plaintext equivalent, measured on the same machine: 6.4 microseconds for the identical degree‑14 polynomial evaluation in plain numpy. That puts encrypted evaluation at roughly 10⁵ to 2×10⁵ times the plaintext cost — five orders of magnitude is the actual price of keeping the input encrypted throughout, not a rounding error to plan around.

A CKKS ciphertext is, by design, computationally indistinguishable from random noise — that's the security property doing its job — so general‑purpose compression finds nothing to exploit and zstd reliably makes it slightly larger (frame overhead on incompressible data). The Java and Python depth‑14 sizes aren't a controlled comparison: Java's number comes from SEAL's raw Ciphertext_Save, which drops the consumed primes' data as levels are used up. Python's number comes from TenSEAL's own serialize(), whose format and defaults are opaque from the outside — it doesn't shrink the way the raw SEAL size does, and that discrepancy is reported honestly here rather than explained away. Treat the Java numbers as the more trustworthy read on "cost per level," and the Python number as "cost of this particular wire format."
Production viability

What this means for scaling

The workload is genuinely stateless in the way that matters for horizontal scaling: the context and public keys are fixed, shared, boring infrastructure; every request is encrypt → evaluate → decrypt with no session state carried between requests. That means capacity is a straight multiply — no coordination tax, no sticky sessions, no shared cache to keep warm. The catch is what each request costs on its own.

100 requests/second is an arbitrary yardstick, not a real target — the point is the shape of the number. This is CPU‑bound, single‑core‑pinned work (SEAL doesn't multithread a single evaluation), so the honest scaling story is add cores linearly, not cleverness: no amount of caching or batching changes that one evaluation eats most of a CPU core for the better part of a second to two seconds. Vertical scaling (bigger boxes) and horizontal scaling (more boxes) are equally valid here since there's no shared state to fight over — pick whichever is cheaper on the target cloud, not which "handles load better," because both scale identically: linearly, per core, with no discount for scale.

A service that evaluates orbital state on every poll or every conjunction check would need to budget roughly one CPU‑second per evaluation at this depth, and that budget grows with polynomial degree and multiplicative depth, not with request complexity in the way a normal API would. Sizing for this means sizing for the number of concurrent evaluations, full stop.

Findings

Bad and good, without rounding up

What doesn't hold up

Five orders of magnitude slower than plaintext.6.4 µs in the clear vs 660 ms–2.1 s encrypted for the identical polynomial. This is the actual price of the approach, and it's steep.
Depth is a hard, pre‑committed budget, not a tuning knob. This context supports exactly 16 sequential multiplications and fails on the 17th, deterministically, in both languages. Widening the eccentricity range in the prototype (stage 6) needed depth ~20+ and simply couldn't run on this context at all — the fix costs a bigger modulus chain, which costs more of everything else in this report.
Per‑core throughput is low. Well under one full evaluation per second per core for the bivariate case. Scaling to real traffic means real hardware spend, linearly, with no batching discount available.
The Java bridge leaks native memory unless you manage it by hand. SEAL's C API has no GC across the JNA boundary — this benchmark run itself crashed with an OOM kill before the fix went in. Any production Java integration on this bridge needs the same discipline this report needed just to finish running.
This protects orbital phase, not orbit identity — and that's a narrower privacy property than it sounds. Orbit shape has to be public to build the offline polynomial fit. For an already-cataloged object that's not a new leak, but for an uncataloged object, or for hiding which object a customer is even asking about, this design exposes exactly the fact that needed protecting. See Privacy model for the full reasoning — this isn't a minor caveat.

What holds up

Correctness is solid and consistent. Both stacks land within centimeters to sub‑meter accuracy of the plaintext SGP4‑shaped ground truth, and Java reproduces the Python prototype's numbers and failure points exactly — same depth ceiling, same error magnitudes.
One‑time costs are genuinely one‑time. Context and key generation (~590 ms) happens once at boot and is shared across all requests — it doesn't belong in per‑request latency budgets, and it doesn't grow with traffic.
The primitives are fast and predictable. Add, multiply‑by‑plaintext, and mod‑switch are all sub‑10ms; ciphertext‑ciphertext multiply is a steady ~85 ms in both stacks. Depth cost is known in advance, before a single value is encrypted — real capacity planning is possible precisely because this isn't data‑dependent.
The scaling model is simple. Genuinely stateless, no coordination between requests, no session affinity — capacity is cores × throughput‑per‑core, which is the easiest kind of system to size and to autoscale.
Compression doesn't need to be built. Don't spend engineering time on ciphertext compression for this transport — the data proves it doesn't help, which simplifies whatever wire protocol carries these.

Orbital mechanics and algorithm terms

Semi-major axis
Half the longest diameter of an elliptical orbit — sets its overall size.
Eccentricity
A number from 0 (circular) to just under 1 (highly elongated) describing how stretched an orbit is.
Mean anomaly
An angle that increases at a constant rate over one orbit — a simple stand-in for "where in time" an object is.
Eccentric anomaly
An angle describing where an object is along its ellipse, geometrically related to but distinct from its true position angle.
Newton–Raphson
An iterative root-finding method that refines a guess using the function's slope; needs division at every step.
Horner's method
A way of evaluating a polynomial with the fewest possible multiplications, by nesting it.
Ordinary least squares
A curve-fitting method that picks coefficients minimizing total squared error against sampled data.
Modulus chain
The ordered list of primes a CKKS ciphertext is defined over; shrinks by one prime every time it's rescaled.
Relinearization
A cleanup step after every ciphertext-ciphertext multiply that shrinks the result back to normal size.
Rescaling
A step after every ciphertext-ciphertext multiply that keeps the scale under control, at the cost of one level of remaining depth.
Off-heap
Memory allocated outside a managed runtime's own heap — e.g. by a native library — invisible to that runtime's own memory accounting.
